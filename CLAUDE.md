# xstyle

Config-driven style engine that converts typed style objects into atomic CSS classes. Users describe design tokens in `xstyle.config.ts`; CSS is pre-generated by the CLI or the Vite plugin; the typed runtime `css()` only assembles class names.

## Stack

- TypeScript (strict), **pnpm**
- **Vite** library mode for the build (multi-entry: `index`, `cli`, `vite`), **Vitest** for tests
- ESLint (`@atolye15/eslint-config`) + Prettier + `tsc` for linting
- Runtime deps: `jiti` (config evaluation), `chokidar` (watch); `vite` is an optional peer

## Commands

```bash
pnpm test             # Vitest (run once)
pnpm lint             # eslint + tsc
pnpm format           # Prettier + eslint --fix
pnpm build            # Vite library build → dist/
```

## Invariants

These come from the approved refactor plan (`.claude/plans/standalone-refactor.md` — plans are working logs, kept local and gitignored; the durable decisions are distilled into this file):

- **One key grammar** — `styleName-token[@bp]` — is the single contract between codegen and runtime. Class names are derived from it by a pure function in `src/shared/class-name.ts` (`hashed` or `readable` mode); there is no mapping module. `makeClassName` returns the *unescaped* class name (what goes into the `class` attribute); selectors escape it at codegen time.
- `src/shared/`, `src/config/`, `src/infer/`, `src/presets/`, `src/runtime/` must stay isomorphic (no Node built-ins/globals); Node-only code lives under `src/node/`, `src/cli.ts`, `src/vite.ts`. The tsconfig loads `node` types, so isomorphism is by convention — watch for it in review.
- Types are inferred from the user config end-to-end (`defineConfig` → `createXStyle`); no type codegen. Never annotate configs with `XStyleUserConfig` (kills literals — documented pitfall, covered by a type test).
- No arbitrary values: all CSS is pre-generated from the config; the runtime only assembles class names.
- The hash wire format (djb2-xor → base36, 6 chars) is pinned by a test table in `class-name.test.ts`; changing it breaks every generated stylesheet.
- `theme` omitted → the built-in `defaultTheme` (`src/config/default-theme.ts`); an explicit theme replaces it wholesale (spread `defaultTheme` to extend). `presets` omitted → `resolveConfig` injects `presetDefault({ theme })` built from that *effective* theme, `presets: []` opts out. Both fallbacks are mirrored at the type level by `ThemeOf`/`RulesOf` in `src/infer/resolve.ts` — value and type level must never diverge. Never index `C['theme']` directly (errors on theme-less configs); go through `ThemeOf<C>`.

## Structure

- `src/config/` — `types.ts` (config/`ResolvedConfig` contracts), `default-theme.ts` (built-in theme: neutral colors + space/size/radius scales), `define-config.ts` (identity + type-level `responsive` validation), `resolve-config.ts` (theme fallback + preset merge + runtime validation; collects errors)
- `src/shared/class-name.ts` — `makeKey` / `makeClassName` / `escapeClassName` + hashing
- `src/infer/` — type-only: `resolve.ts` (`RulesOf`, `MergePresets`), `declaration.ts` (`XStyleDeclarationFor`, …)
- `src/presets/` — `to-named-values.ts`, `default/` (`buildDefaultRuleGroups(theme)` → 10 named groups, flattened by `buildDefaultRules(theme)`; `presetDefault({ theme, exclude?, excludeGroups? })` drops rules/groups at value and type level; group → rules reference in `default/README.md`)
- `src/runtime/create-xstyle.ts` — `createXStyle(config) → { css }`; dev-mode key validation, prod pure
- `src/codegen/generate-css.ts` — `generateCSS(resolved)`; key-ambiguity + hash-collision detection
- `src/node/` — `load-config.ts` (jiti discovery/eval + dependency list), `build-css.ts` (shared CLI/plugin core)
- `src/cli.ts` (`runCli` — `build`/`watch`) + `bin/xstyle.mjs`; `src/vite.ts` (`virtual:xstyle.css` plugin)
- `test/fixtures/` — configs evaluated by jiti in tests (not linted/typechecked)

Type tests (`expectTypeOf` + `@ts-expect-error`) live in regular `*.test.ts` files and are enforced by `pnpm lint:ts`, not by Vitest.

## Workflow

- After finishing a task run `pnpm lint`, `pnpm test`, and `pnpm build`, in that order (see the `verify` skill).
- Commit with conventional commits via the `commit` skill. Never commit to `main` once the repo has a remote; until then, keeping the refactor history linear on `main` is fine.
- Every change lands through a PR merged with a merge commit (no squash or rebase). PR titles are plain sentences without a conventional commit prefix: the merge commit message is the PR title and release-please reads it, so a `fix:` title would add the change to the changelog twice.

## Releases

- release-please opens a release PR from the conventional commits on `main`. Tags are `vX.Y.Z` (no package name). Below 1.0.0, breaking changes bump the minor version and features bump the patch version.
- Merging the release PR tags the release, and `.github/workflows/release.yml` runs the tests and the build, then stages the version on npm with `npm stage publish --provenance`. It goes live only after a maintainer approves it with 2FA (npmjs.com "Staged Packages" tab or `npm stage approve <stage-id>`).
- If publishing fails for a release, run the Release workflow manually with the existing tag (e.g. `v0.1.1`) to stage it again.
- Manual edits to a release PR (e.g. changelog notes) are lost if anything else lands on `main` before it is merged, because release-please regenerates the PR.
